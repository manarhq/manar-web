# Manar — SOC Console Visual Redesign

You are working on **`manar-web`**, the operator console for **Manar**
(منار) — a federated AI-agent governance platform built at Vax Labs for
security operations teams. Next.js 16 (App Router), React 19,
Tailwind 4, TanStack Query + Table, `next-intl` with full EN/AR and RTL,
and a TypeScript API client generated from `manar-api`'s live OpenAPI
document.

**The brief: rewrite the UI to feel futuristic and calm — easy on the
eyes over a long shift.** You have latitude on components and libraries.
You do not have latitude on the constraints in the next section.

---

## What this console actually is

Read this before touching a pixel. It determines whether "futuristic"
lands or backfires.

Manar governs what autonomous AI agents are permitted to do inside a
security operations centre. Every screen answers one of: _what is this
agent allowed to do, what did it just try, who approved it, and can I
prove it afterwards._ The audit trail is hash-chained and exportable as
signed evidence — legal artifacts, not dashboards.

The people using this are SOC analysts reading it for hours, often while
something is going wrong, sometimes at 3am. So:

- **Futuristic means confident restraint, not spectacle.** Precision,
  depth, and quiet motion. Not neon glow, not scanlines, not HUD
  crosshairs, not a Blade Runner pastiche. If a screenshot would look at
  home in a film about hackers, it is wrong.
- **"Simple for the eyes" is the harder half of the brief and the one
  that matters more.** Low-glare dark surfaces, generous spacing,
  restrained motion, no unnecessary contrast churn, nothing that pulses
  or animates in peripheral vision while someone reads a table.
- **Legibility under stress beats novelty every time.** If a choice looks
  striking in a screenshot but costs a tired analyst half a second to
  parse, it loses.

## Hard constraints — do not break these

These are correctness properties, not preferences. If a visual idea
requires breaking one, drop the idea and note it in your report.

1. **Risk semantics.** Band _thresholds_ live in `lib/risk.ts` and are
   tested — do not touch them. The 5-band ramp
   (`--risk-minimal` → `--risk-critical`) must remain **distinguishable
   at a glance and monotonic**: an analyst must be able to tell critical
   from high without reading a label. You may restyle the ramp; you may
   not flatten it into a decorative gradient, and you may not encode risk
   in colour alone (colour-blind analysts exist — keep a shape, label, or
   position cue alongside).
2. **`--state-safe` stays reserved** for verified / active / success. It
   is never a generic accent. This rule already exists in
   `app/globals.css` because an earlier iteration violated it.
3. **RTL and i18n.** EN and AR key counts are currently at **exact parity
   (714 / 714)** — keep them exact. Every new string needs both files.
   Use logical CSS properties (`ms-*`, `me-*`, `ps-*`, `pe-*`,
   `start-*`, `end-*`), never `ml-*`/`pl-*`/`left-*`. Arabic text must
   render correctly in RTL after this rework — `__tests__/rtl.test.tsx`
   must still pass, and extend it if you add layout primitives.
4. **Never hand-edit `lib/api/schema.d.ts`.** It is generated by
   `pnpm api:codegen` from `manar-api`'s OpenAPI document. If a page
   needs a field the schema lacks, that is a backend conversation, not a
   frontend edit.
5. **Do not change data semantics to suit a layout.** No inventing
   fields, no faking values to fill a chart, no hardcoded sample data
   left in a component. If a screen looks sparse because the API returns
   little, design a better empty state — do not fabricate content.
6. **Preserve the fail-safe honesty of the AI panels.** The three
   AI-advisory surfaces — `components/manar/incidents/incident-summarize-panel.tsx`,
   `components/manar/policies/suggest-policy-dialog.tsx`,
   `components/manar/audit/audit-investigate-panel.tsx` — must keep:
   AI output visibly marked as advisory and unsaved; the `available:
false` state rendered as a calm "no AI response right now," never as a
   crash; and the elapsed-time affordance (`hooks/use-elapsed-seconds.ts`)
   — a real call can legitimately take 30+ seconds and the user must not
   think it hung. Keep `retry: false` on those mutations.
7. **`prefers-reduced-motion` must be honoured** everywhere you add
   motion. Not as an afterthought — as the condition on every transition
   you write.
8. **Accessibility floor:** WCAG AA contrast on all text, visible focus
   rings on every interactive element (the console must be fully
   keyboard-navigable — Cmd+K already is), semantic HTML, real labels on
   every input. A "futuristic" low-contrast look that fails AA is a
   failed brief, not a style choice.
9. **`manar-web` only.** No changes to `manar-api` or `manar-ai`. No
   Kubernetes, DNS, TLS, or deployment work.

## Where the design is now

The console has already had one deliberate design pass — read
`docs/design-rework.md` first. It replaced an earlier flat-teal palette
with a dark instrument-panel language: deep cold-near-black surfaces, a
single amber/signal-gold accent (`#E9A23B`), a reserved safe-green, and
the 5-band risk ramp. Tokens are oklch CSS custom properties in
`app/globals.css` (182 lines, `:root` light + `.dark` default).

**This is a second pass on considered work, not a rescue of something
templated.** Treat the existing palette as a starting position with a
rationale. You may evolve it — including replacing the amber accent if
you can argue something better — but read the reasoning before
overriding it, and say in your report what you changed and why.

What exists today: 84 components under `components/manar/`, 20 primitives
under `components/ui/`, sidebar with Monitoring / Governance /
Administration grouping, breadcrumbs, Cmd+K command palette, sidebar
attention counts, `RiskBadge` / `RiskMeter`, `DataTable`, `EmptyState`,
`StatTile`, `PageHeader`.

## Latitude — you may add libraries

Currently available: `@base-ui/react`, `lucide-react`, `sonner`,
`tw-animate-css`, `zustand`, `class-variance-authority`, TanStack Query
and Table, and the `shadcn` CLI as a devDependency.

**Notably absent: any real animation library.** If you want physics-based
motion, add one (`motion` / Framer Motion is the obvious choice). Same
for charting — there is no chart library, and the Overview dashboard and
risk visualisations would benefit from one.

Any library you add must clear this bar:

- Actively maintained, compatible with React 19 + Next 16 App Router,
  works with SSR (or is correctly client-boundaried).
- Adds real value a hand-rolled component wouldn't. Do not add a
  dependency for a single rounded box.
- **Log it in `docs/dependency-decisions.md`** in the existing format —
  Technology / Purpose / Version / License / Docs consulted / Install
  method / Why / Alternatives considered. This repo has maintained that
  discipline from Phase 1; do not break it now.
- Bundle cost is a real consideration. Check what it does to
  `pnpm build` output and report it.

## Direction — what "futuristic and calm" means concretely

Interpret these; don't execute them literally.

- **Depth over decoration.** Layered surfaces, considered elevation, real
  hierarchy in how panels sit against the background. Not borders
  everywhere and not shadow-soup.
- **Typography carries more weight than colour.** A disciplined type
  scale with genuine hierarchy will do more for "futuristic" than any
  effect. Consider a technical/geometric face for numerals and IDs and
  something highly legible for body text. Tabular numerals in every
  table and metric — misaligned digits read as amateur instantly.
- **Motion is a state-change signal, not a flourish.** Fast (150–250ms),
  eased, and only where something actually changed. The live audit feed
  is the one place motion carries real meaning — new events arriving.
  Get that right and leave the rest still.
- **Density is a feature.** Analysts scan; they don't scroll for fun. Aim
  for high information density that still breathes. Empty-state voids
  and oversized cards were called out as problems in the last pass —
  don't reintroduce them.
- **The Overview page is your showcase.** It should read as a real
  operations dashboard: what needs attention now, what agents are doing,
  where risk is concentrated. This is the first screen anyone sees.
- **Data must stay humanised.** The last pass fixed raw UUIDs and
  `dot.notation` event strings leaking into the UI — keep those
  utilities (`hooks/use-actor-name.ts` and the event-humanisation
  helpers) and extend the same discipline anywhere you touch.
- **Arabic deserves equal design attention.** Test the RTL layout as you
  build, not at the end. Arabic typography has different vertical rhythm
  and line-height needs than Latin — if your type scale only looks right
  in English, it is half-finished.

## Sequencing

Work in this order; do not start page reworks before the foundation
lands, or you will redo them.

1. **Foundation** — tokens in `app/globals.css`, type scale, spacing and
   elevation system, motion primitives, and the shared primitives in
   `components/ui/`. Land this and verify RTL + contrast before moving on.
2. **Shared `components/manar/` pieces** — `DataTable`, `RiskBadge`,
   `RiskMeter`, `StatTile`, `EmptyState`, `PageHeader`, `Breadcrumbs`,
   sidebar, topbar, command palette.
3. **Overview**, rebuilt as a real dashboard.
4. **Remaining pages**, in this order: Agents, Approvals, Audit, Tasks,
   Incidents, Policies, Tools, then Compliance / Integrations / Users /
   Roles / Settings.
5. **The three AI panels last**, so they inherit the finished language —
   respecting constraint 6 exactly.

Commit at each numbered step so the work is reviewable and reversible.

## Verification

"It compiles" is not evidence a visual change worked.

```bash
cd manar-web
pnpm lint && pnpm typecheck && pnpm test && pnpm build
```

Then, with a real stack running (`manar-api`'s `pnpm infra:up` +
`pnpm start:dev`, and `pnpm manar demo:seed` for data), take real
headless-browser screenshots — `playwright` is already a devDependency
and `scripts/verify-e2e-smoke.mjs` is the existing pattern to follow:

- Every page, **in both `en` and `ar`**, at desktop width.
- At least Overview, Agents, Approvals, and Audit at a narrow width too.
- Both states of each AI panel: real result, and `available: false`.
- Look at them. If something is misaligned, low-contrast, or visually
  broken in RTL, fix it before reporting done.

Also verify: full keyboard navigation with visible focus throughout;
Cmd+K still works; contrast checked against WCAG AA (measure, don't
eyeball); the layout with `prefers-reduced-motion: reduce` set.

## Reporting

When finished, write a short report covering: the design direction you
chose and why, what you changed about the existing palette and the
reasoning you were overriding, every library added with its bundle cost,
which constraints above forced you to abandon an idea, how RTL and
contrast were verified (with numbers, not assertions), and anything you
think is now worse than before. If something in this brief conflicts with
what the code actually needs, say so rather than working around it
silently.
